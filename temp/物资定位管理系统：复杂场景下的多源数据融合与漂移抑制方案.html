物资定位管理系统：复杂场景下的多源数据融合与漂移抑制方案

基于之前的架构，我们深入分析边界区域、信号遮挡、室内外过渡及静止漂移等极端场景。这些场景是定位算法最容易失效的“深水区”，需要设备端（Air780EG + NRF52832）与平台端紧密配合。

1. 核心场景时序与数据存在性矩阵

场景一：UWB/BLE 与 GNSS 交界边界区域（半室内/走廊/窗口）

背景：设备在建筑物边缘移动，GNSS 信号受墙体遮挡出现多径效应，UWB/BLE 信号时断时续。

时间点 物理环境 GNSS 状态 (Air780EG) UWB/BLE 状态 (NRF52832) 平台接收数据组合 平台处理策略
T1 靠近窗口 Fix Quality=1, HDOP>3.0 (精度差) UWB 测距成功 (3个锚点) GNSS (低质) + UWB 权重倾斜：降低 GNSS 权重，以 UWB 解算坐标为主。若两者偏差 > 10m，丢弃 GNSS。
T2 进入走廊 Fix Quality=0 (无信号) BLE 扫描到 2 个 Beacon 仅 BLE 相对位移推算：利用上一时刻 UWB/GNSS 坐标为起点，根据 BLE RSSI 变化趋势估算移动方向。
T3 走出走廊 搜星中 (冷启动) UWB 恢复连接 仅 UWB 快速重定位：UWB 提供绝对坐标，填补 GNSS 搜星期间的 30-60s 空白。
  • 代码体现：
    • gnss_main.c 中 nmea_parse_packet 会根据 hdop 和 num_satellites 评分。
    • _client.c 的 gnss_point_score 函数会给高 HDOP 的数据打上高分（惩罚），平台应识别此分数。

场景二：室内运动但 GNSS 仍有弱信号（“伪室外”陷阱）

背景：设备在大型商场或厂房内部运动，GNSS 能收到 6-8 颗卫星，但由于非视距传播（NLOS），定位点会漂移到室外街道或相邻楼层。此时 NRF52832 正常扫描到室内 UWB/BLE。

模块 实际表现 数据特征 风险点
GNSS 持续输出坐标 fix_quality=1, mode='A', 但坐标在墙外跳动 严重漂移：平台误以为设备在室外高速移动。
UWB/BLE 稳定输出室内坐标 距离/Beacon ID 对应室内地图位置 真相：反映设备真实室内位置。
Sub-1G 1Hz 发布运动标志 motion_flag = 1 确认设备处于活跃状态。
  • 平台融合逻辑（关键）：
    1. 地理围栏校验：平台判断 GNSS 坐标是否落在“已知室内区域”的多边形外。
    2. 冲突检测：若 Distance(GNSS, UWB) > 阈值(如 20m)，且 UWB 信号强度良好（RSSI > -80dBm）。
    3. 决策：强制屏蔽 GNSS。标记该时间段为“室内模式”，轨迹完全由 UWB/BLE 驱动。

场景三：设备静止但 GNSS 漂移（“鬼影”移动）

背景：设备放在桌上静止。由于大气扰动或多径，GNSS 坐标在几十米范围内随机游走。此时 NRF52832 因加速度计未触发而休眠，无 UWB/BLE 数据。

时间点 传感器状态 Air780EG 行为 平台接收数据 优化方案
T0 静止检测成功 关闭 GNSS 电源 无新数据 完美：无数据即无漂移。
T0+5min 误判为运动（震动） 开启 GNSS，40s 后上报 仅 GNSS (漂移点) 速度滤波：平台计算两点间速度，若 $V > 5km/h$ 且无 Sub-1G/NRF 运动佐证，判定为漂移。
T0+10min 持续静止 再次进入休眠 30min 快照 位置吸附：将后续所有点吸附回 T0 时刻的坐标。
  • 代码改进建议：
    • 在 gnss_main.c 的 is_device_stationary 逻辑中，增加加速度计原始数据校验，防止仅靠 GNSS 速度为 0 就判定静止（因为漂移时 GNSS 速度也可能瞬间为 0）。

场景四：UWB/BLE 失败但 GNSS 良好的“反向”场景

背景：设备在开阔地带，但 UWB 锚点故障或 BLE 信标电池耗尽。

模块 状态 平台策略
GNSS HDOP < 1.5, 卫星 > 10 主用：信任 GNSS 数据。
UWB/BLE 超时/无数据 辅助缺失：平台记录“室内定位组件离线”告警。
Sub-1G 正常 维持心跳。

2. 平台端高级漂移抑制算法细节

针对上述场景，建议平台端实现以下三层过滤网：

第一层：合理性校验（硬过滤）

  • 最大速度限制：若两点间计算速度 $> 120 km/h$，直接丢弃后一点。
  • 高度跳变限制：若海拔高度瞬间变化 $> 50m$（非电梯场景），视为无效。
  • 信号质量门限：
    • 若 HDOP > 3.0 且 同时存在 UWB/BLE 数据 $\rightarrow$ 丢弃 GNSS。
    • 若 fix_quality == 0 $\rightarrow$ 仅当无其他数据时才勉强使用（用于显示大概区域）。

第二层：多源一致性校验（软融合）

  • 卡尔曼滤波 (EKF) 状态向量：
    $$
    X = [x, y, v_x, v_y, b_{gnss}]^T

    $$

    其中 $b_{gnss}$ 是 GNSS 的系统偏差。

  • 观测更新：

    • 当 UWB 数据到来时，作为高置信度观测值，修正 $x, y$。
    • 当 GNSS 数据到来时，若其与预测值偏差过大，增大 $b_{gnss}$ 的协方差，降低其权重。

第三层：业务逻辑校正（语义理解）

  • 道路匹配 (Map Matching)：若 GNSS 点偏离道路中心线 > 15m，但 BLE 显示在路边店铺内，则将点吸附到店铺坐标。
  • 静止锁定：
    • 若连续 3 个周期（约 2min）未收到 NRF52832 的运动触发，且 GNSS 速度波动 < 0.5m/s。
    • 平台强制将轨迹“拉直”，所有点合并为一个静态图标。

3. 补充细节需求清单（请确认）

为了完善方案，我需要您补充以下细节：

  1. UWB/BLE 的“失败”定义：

    • 是 NRF52832 根本扫描不到任何标签？
    • 还是扫描到了但解算失败（如锚点不足 3 个）？
    • 代码中是否需要区分 num_nodes=0 和 parse_error？

  2. Sub-1G 的运动标志来源：

    • 目前代码中 _device_motion_notify 依赖 NRF52832 传来的 motionflag。
    • 如果 NRF52832 休眠了，这个标志位会保持上一次的状态吗？这会导致 GNSS 模块误判。

  3. 室内地图支持：

    • 平台端是否有室内 CAD/矢量地图？
    • 如果有，我们可以实现更精准的“墙体外推抑制”；如果没有，只能依赖纯几何算法。

  4. GNSS 弱信号的具体指标：

    • 您提到的“6-8 颗星但漂移严重”，通常伴随 HDOP > 2.5 或 C/N0 较低。
    • 代码中是否需要增加对 C/N0（信噪比）的采集和上报？目前 NMEA 解析似乎只取了 hdop 和 num_satellites。

4. 总结：全场景数据流向图

下一步建议：
如果您能提供 NRF52832 在静止时的 SPI 通信行为（是完全不发数据，还是发空包？），我可以进一步优化 11_nrfcomm_v2.c 中的状态同步逻辑，防止“假运动”导致的 GNSS 频繁启停。

这是一个非常关键的硬件行为约束。NRF52832 在静止时完全停止 SPI 通信，意味着 Air780EG 无法通过“接收空包”来感知 NRF52832 的存在或状态。

这会导致以下三个核心风险，需要在代码逻辑中进行针对性处理：

1. “假离线”与任务崩溃风险

  • 现状：在 11_nrfcomm_v2.c 的 nrfcomm_spi_task 中，有一个 error 计数器。如果连续 100 次 CRC 校验失败（因为没数据，CRC 肯定对不上），代码会执行 break 并删除任务。
  • 后果：设备静止超过一定时间（取决于 SPI 交换频率，约 100s），NRF 通信任务会自杀。当设备再次运动时，由于任务已删除，SPI 不再工作，导致 UWB/BLE 数据永久丢失。
  • 解决方案：必须修改 nrfcomm_spi_task，使其在检测到 NRF52832 休眠（无响应）时进入低功耗等待模式，而不是报错退出。

2. 运动状态同步延迟（Motion Flag 滞后）

  • 现状：GNSS 模块依赖 _device_motion_notify(ms) 来决定是否开启电源。这个标志位来自 NRF52832 的 SPI 数据包。
  • 后果：
    • 从静到动：NRF52832 唤醒并开始发包需要时间（加速度计检测 + 射频启动）。在这几秒的“真空期”，Air780EG 仍认为设备是静止的，可能导致 GNSS 开启延迟，错失第一波定位机会。
    • 从动到静：NRF52832 突然断联。Air780EG 会保留上一次收到的 motionflag=1。如果不做超时处理，GNSS 模块会误以为设备还在运动，继续每 40s 开启一次电源，造成严重的功耗浪费。

3. Sub-1G 数据的独立性

  • 确认：既然 NRF52832 静止时不发 SPI 数据，那么 Sub-1G 的 1Hz 发布逻辑完全是 NRF52832 内部闭环的。Air780EG 只有在 NRF52832 醒来并通过 SPI 上传历史缓存或实时数据时，才能拿到 Sub-1G 的状态信息。

代码优化建议 (针对 Air780EG 端)

为了适配“静止即断联”的特性，建议对 11_nrfcomm_v2.c 进行如下微调：

A. 防止任务自杀 (修改 nrfcomm_spi_task)

将原来的 break 逻辑改为“休眠等待”，并增加一个“心跳超时”判定来重置运动状态。

B. 增强 GNSS 端的鲁棒性 (gnss_main.c)

在 gnss_setup_task 中，除了依赖 _device_motion_notify，建议增加一个本地看门狗：

  • 如果超过 GNSS_DETECT_DOWN_INTERVAL (如 5分钟) 没有收到任何有效的 GNSS Fix 且没有收到 NRF 的运动标志，强制进入深度睡眠。

平台端融合策略更新

基于“静止无 SPI 数据”的事实，平台端的轨迹优化逻辑应调整为：

场景 设备端表现 平台端接收特征 平台处理逻辑
静止期 NRF 休眠，GNSS 关闭 长时间无任何数据包 位置锁定：保持图标在上一个坐标不动。若超过 30min 收到一条“静止快照”，则更新坐标。
起步瞬间 NRF 唤醒，SPI 恢复 先收到 BLE/UWB，后收到 GNSS 预加载：利用 BLE/UWB 数据先在地图上画出起始段，避免等待 GNSS 搜星导致的“起步空白”。
进入室内 NRF 正常工作，GNSS 漂移 BLE/UWB 连续，GNSS 跳变 信号源切换：一旦检测到 BLE/UWB 信号强度稳定且 GNSS HDOP 恶化，立即切断 GNSS 权重，转为纯室内地图匹配。
NRF 故障 NRF 损坏，始终无 SPI 仅有 GNSS 数据 降级运行：平台标记“室内定位组件离线”，仅依靠 GNSS 进行室外轨迹追踪，并上报告警。

总结

“静止不发数据”实际上是一种优秀的低功耗设计，但它要求 Air780EG 必须具备**“失联即静止”**的默认假设。
