显示内容

如何在设备屏幕上显示内容

以往我们学习单片机的时候，我们会初始化一个和屏幕大小的数组，然后对数组内容进行修改，修改后的数据发送到屏幕上，就可以在屏幕上显示我们设置的数组内容。
而Linux也是通过类似的方式，只不过Linux把显示设备抽象为一个文件，在我们板卡中是/dev/fb0，fb是FrameBuffer的缩写，中文译名为帧缓冲驱动，
Linux抽象出FrameBuffer这个设备来供用户态进程实现直接写屏。 FrameBuffer机制模仿显卡的功能，将显卡硬件结构抽象掉， 可以通过FrameBuffer的读写直接对显存进行操作。 用户可以将FrameBuffer看成是显示内存的一个映像， 将其映射到进程地址空间之后，就可以直接进行读写操作， 而写操作可以立即反应在屏幕上。

如上图所示，屏幕中每个像素的显示颜色由4个byte组成，其实就是ARGB格式

所以，我们对/dev/fb0的数据写入，就是显示数据的写入。所以，我们就可以下发代码实现屏幕的刷新，当然了这些代码不用去背，大致了解原理即可。

ioctl（Input/Output Control）用于对设备进行控制操作，例如配置硬件参数、获取设备信息（如终端、帧缓冲设备 /dev/fb0、串口等）交互。

git 简略使用指南

1. 核心概念 (必读)

在输入命令之前，理解 Git 的“三个区域”至关重要：

  1. 工作区 (Working Directory): 你电脑里能看到的文件夹，你在这里修改文件。
  2. 暂存区 (Staging Area/Index): 一个临时区域，保存了你打算提交的修改（git add 后的状态）。
  3. 版本库 (Repository): 存储所有历史版本的地方（git commit 后的状态）。

基本流程： 修改文件 添加到暂存区 提交到版本库。

建议的最佳实践

  1. 勤提交： 尽量保持原子性提交（一个 Commit 只做一件事），方便回滚。
  2. 写好 Commit Message： 清楚地描述“做了什么”，而不是“更新了代码”。
  3. 不要提交大文件/敏感文件： 使用 .gitignore 文件来忽略不需要版本控制的文件（如密码文件、编译生成的 node_modules 或 dist 目录）。

可维护性 差，项目结构或依赖关系变化时，需手动调整编译命令，容易遗漏或出错 较好，在Makefile中清晰定义文件依赖和编译规则，修改和拓展项目时只需要调整Makefile内容。 好，CMakeLists.txt文件独立于具体平台和构建工具，修改项目配置时只需修改该文件，CMake会重新生成相应构建文件。
适用场景 小型项目、学习阶段或需快速验证代码的情况。 中等规模项目，项目结构相对稳定、依赖关系明确。 大型项目、跨平台项目或需与不同开发工具继承的项目。

嵌入式结构体设计的对齐与优化

在嵌入式系统开发中，结构体的内存布局直接影响程序的内存占用和访问效率。

内存对齐

什么是内存对齐

内存对齐是指数据在内存中存储时，其起始地址必须是某个特定值的倍数。例如：

  • char类型（1字节）：可以存储在任意地址
  • int类型（4字节）：通常要求存储在4字节对齐的地址（如0x0000, 0x0004, 0x0008…）
  • double类型（8字节）：通常要求存储在8字节对齐的地址

为什么要关注内存对齐

在嵌入式系统中，内存对齐主要影响两个方面：

  1. 访问效率 ：ARM Cortex-M系列CPU访问对齐数据时只需1个时钟周期，而访问非对齐数据可能需要2-3个时钟周期，甚至触发硬件异常（如Cortex-M0不支持非对齐访问）。
  2. 内存占用 ：不合理的结构体设计会产生大量填充字节，浪费宝贵的RAM和Flash资源。

对齐vs非对齐访问验证

内存对齐规则

基本对齐规则

编译器遵循以下对齐规则：

  1. 第一个成员 ：永远放在结构体起始位置（偏移量0）
  2. 后续成员 ：每个成员的起始地址必须是「成员类型对齐值」的整数倍
  3. 结构体整体 ：总大小必须是「所有成员中最大对齐值」的整数倍

对齐值定义

类型 大小（字节） 典型对齐值（字节）
char 1 1
short 2 2
int 4 4
float 4 4
double 8 8
指针 4/8 4/8（取决于CPU架构）

Protocol Buffers

什么是 Protocol Buffers？

Protocol Buffers 是 Google 开源的结构化数据序列化机制，特点是：

• 体积小：二进制编码，远小于 JSON/XML；
• 速度快：序列化/反序列化速度快，开销低；
• 强类型：使用 .proto 文件定义字段，自动生成代码，避免类型错误；
• 版本兼容：字段有标签号（tag），支持新增字段而不破坏旧版本；
• 多语言支持：官方支持C/Java/Python/Go 等多种语言。
对比 JSON：

特性 JSON Protocol Buffers
编码 文本 二进制
体积 大 小（通常为 JSON 的 1/3~1/10）
解析速度 慢，需要字符串解析 快，直接操作字节流
强类型 无 有（由<span leaf="">.proto</span> 定义）
版本兼容 依赖字段名称 依赖字段编号，兼容性更强
适用于嵌入式 一般 非常适合

Protobuf 数据模型
一个 Protobuf 消息由字段组成，每个字段具有：

• 类型（int32、string、bytes 等）
• 名称（如 temperature）
• 标签编号（tag，比如 1）

nanopb

为什么需要 nanopb？
标准的 Protobuf C/C++ 库体积较大，依赖动态内存分配，不适合资源受限的 MCU。nanopb 为嵌入式平台量身打造，具有以下特点：

• 超小体积：核心库仅几 KB，生成的代码也极小；
• 无动态内存：默认使用静态缓冲区，避免 malloc/free 带来的风险；
• 可配置性强：可以按需启用/禁用字段、回调；
• 开源：遵循 zlib 许可证，商业友好；
• 兼容 Protobuf：与官方工具链兼容，可与手机 App、服务器使用的 Protobuf 无缝对接。

    • PC 端工具使用 Protobuf 解析日志

总结

借助 Protocol Buffers + nanopb，可以在嵌入式设备建立一种高效、可靠、可扩展的数据交换机制，轻松应对复杂数据结构和跨平台兼容性问题。
