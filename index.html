FreeRTOS工程化要点：任务划分、优先级设计与CPU占用率监控

FreeRTOS任务怎么拆？优先级怎么配、CPU占用怎么看？

## 一、任务划分原则

1、单一职责：一个任务只干一件事

把”串口接收 + 数据解析 + 指令执行 + 结果反馈”全塞一个任务，解析环节一出问题整条链路全挂，而且任务执行时间拉长后会阻塞其他高优先级任务。

正确做法：按照职责拆成各独立任务，通过队列串联，某一环节异常不影响其他环节。

2、低耦合与合理粒度

任务间数据传递走队列、任务通知、事件组，别直接读写全局变量。任务数量上，一般中小项目控制在 5~8 个 比较合理——太少功能挤一起难维护，太多上下文切换开销吃不消。

### 3、轻量化：单次执行控制在10ms以内

空闲任务只有在所有其他任务都阻塞 时才能拿到 CPU。你的任务一跑就是几十毫秒不释放，空闲任务跑不了，低功耗和看门狗喂狗逻辑都会出问题。耗时操作必须拆子任务或分段执行。

二、优先级设计

核心原则：数字越大，优先级越高

这是非常多人搞反的点。FreeRTOS 中空闲任务优先级为 0，是最低 的：

优先级范围是 <span leaf="">0</span> 到 <span leaf="">configMAX_PRIORITIES - 1</span>，数字越大越先执行。分配时，核心实时任务给大数字，后台任务给小数字。非必要别让多个任务共用同一优先级，否则触发时间片轮转，增加切换开销。

任务类型 优先级 说明
故障报警 10 必须最快响应
传感器采集 8 实时性要求高
数据解析/指令执行 6
外设通信（串口等） 4
显示/按键 3
日志/自检 1 仅高于空闲任务

三、CPU占用率监控

CPU 占用率是系统健康度的晴雨表，建议控制在 30%~70%。FreeRTOS 内核原生支持运行时统计（<span leaf="">configGENERATE_RUN_TIME_STATS</span>），每次上下文切换时自动累计每个任务的运行时间，精度高、零应用层计算代码，直接用就行。

3、异常速查

现象 常见原因 优化方向
>80% 死循环无延时、中断过频、资源竞争激烈 拆分耗时任务、降低中断频率
<20% 延时过长、执行频率低 缩短延时、充分利用 CPU
波动大 突发耗时操作、中断源不稳定 分段执行、稳定中断源

四、总结

FreeRTOS 工程落地就三件事：

  1. 任务划分 ——单一职责、轻量化、低耦合，5~8 个任务为宜，别把所有逻辑塞一个任务里，也别拆太碎。
  2. 优先级设计 ——数字越大优先级越高（<span leaf="">tskIDLE_PRIORITY = 0</span> 是最低），核心实时任务给高值，后台任务给低值；共享资源用 <span leaf="">xSemaphoreCreateMutex()</span>，优先级继承内核自动搞定。
  3. CPU 占用率监控 ——开启 <span leaf="">configGENERATE_RUN_TIME_STATS</span>，用 DWT CYCCNT 做时间基准（不占外设），<span leaf="">vTaskGetRunTimeStats()</span> 直接输出每个任务的占比，30%~70% 是健康区间。

自动初始化框架

详细讲解 INIT_HW_EXPORT、INIT_DRV_EXPORT、INIT_TASK_EXPORT 的实现过程

这是一个非常优雅的自动初始化框架，让我从零基础为你详细讲解整个流程。

📚 一、核心概念：这是什么？

这三个宏的作用是：让你定义的函数在系统启动时自动按顺序执行，无需手动调用。

  • INIT_HW_EXPORT: 硬件初始化（如GPIO配置）
  • INIT_DRV_EXPORT: 驱动初始化（如外设驱动）
  • INIT_TASK_EXPORT: 任务初始化（创建用户任务）

优先级关系：HW > DRV > TASK（数字越小优先级越高）

🔧 二、实现原理详解

1️⃣ 宏定义阶段（头文件：luat_init_export.h）

关键点解析：

  • __luat_init_hw_##func: 使用宏拼接生成唯一变量名，例如 demo_hw_level0 变成 __luat_init_hw_demo_hw_level0
  • __attribute__((used, section("luat_init_hw"))): 这是核心！
    • used: 告诉编译器即使这个变量没有被引用也不要优化掉
    • section("luat_init_hw"): 将这个变量放到名为 luat_init_hw 的自定义段中

2️⃣ 链接脚本阶段（.ld 文件或链接器配置）

你看到的 ec7xx_0h00_flash.c 实际上是链接器脚本（虽然扩展名是 .c，但内容是链接脚本语法）。

为什么要改链接脚本？

🎯 链接脚本的作用：告诉 linker（链接器）如何将各个目标文件中的代码和数据组织到最终的二进制文件中。

关键指令解释：

  1. .luat_init_hw : ALIGN(4): 定义一个名为 .luat_init_hw 的输出段，4字节对齐
  2. __start_luat_init_hw = .: 创建一个符号，值为当前地址（段的起始位置）
  3. KEEP(*(luat_init_hw)):
    • *: 匹配所有输入文件
    • (luat_init_hw): 匹配所有名为 luat_init_hw 的输入段
    • KEEP(): 即使没有被引用也保留（防止被优化掉）
  4. __stop_luat_init_hw = .: 创建符号，值为段的结束位置
  5. >FLASH_AREA: 将这些数据放在 FLASH 区域

优势：

  • ✅ 自动化：所有使用该宏的函数自动收集到一个连续区域
  • ✅ 可扩展：新增初始化函数只需添加宏，无需修改其他代码
  • ✅ 解耦：各模块独立，互不依赖
  • ✅ 有序执行：通过 level 控制执行顺序

3️⃣ 编译阶段

当你编译代码时：

  1. 预处理器：将宏展开成带 __attribute__ 的变量定义
  2. 编译器：为每个使用宏的函数生成一个结构体变量，放入对应的段
  3. 链接器：根据链接脚本，将所有 luat_init_hw 段的内容合并到一起，形成连续内存块

总结

这套机制的核心思想是：

  1. 利用 GCC 的 __attribute__((section())) 将数据放到自定义段
  2. 利用链接脚本 将这些段组织成连续内存块，并生成边界符号
  3. 运行时遍历 这些内存块，按优先级执行函数

这是一种在嵌入式系统中非常常见的自动初始化框架设计模式，类似于 Linux 内核的 module_init、RT-Thread 的 INIT_APP_EXPORT 等机制。

Makefile

  • 源码

以下是对您提供的 Makefile 代码的逐行解析 ，重点说明每行的作用、关键逻辑和潜在注意事项：

1. 定义应用路径变量

  • 作用 ：定义应用代码的根目录路径 。
  • 关键点 ：
    • $(TOP)：项目根目录（如./ 或../）。
    • $(TARGET)：目标芯片/平台（如stm32f4）。
    • $(CORE)：内核类型（如arm）。
    • $(PROJECT)：客户/项目名称（如customer1）。
  • 示例 ：若TOP=.、TARGET=stm32f4、CORE=arm、PROJECT=customer1，则路径为./PLAT/project/stm32f4/arm/apps/customer1/airocov_lierda。

2. 添加头文件包含路径

  • 作用 ：将应用层头文件目录和 BSP 适配层头文件目录加入编译器搜索路径。
  • 关键点 ：
    • inc/：应用层头文件（如main.h）。
    • bsp_adapter_inc/：硬件抽象层（BSP）适配头文件（如hal.h）。
  • 注意 ：CFLAGS_INC 是全局编译选项，影响所有源文件。

3. 定义源文件目录

  • 作用 ：指定源文件所在目录。
  • 关键点 ：
    • src/：应用逻辑代码（如main.c）。
    • bsp_adapter_src/：BSP 适配层代码（如hal_stm32.c）。
  • 注意 ：+= 确保追加目录，避免覆盖已有路径。

4. 排除文件列表（留空）

  • 作用 ：定义需要排除 的文件列表（当前为空）。
  • 关键点 ：后续filter-out 会过滤掉这些文件（例如LIOT_AIROCOV_CUSTOMER_APP_EXCLUDE_FILES += file_to_exclude.c）。

5. 收集所有 .c 源文件

  • 作用 ：遍历SRC_DIRS 中的每个目录，收集所有.c 文件。
  • 关键点 ：
    • wildcard：仅匹配当前目录下的一级文件 （不递归子目录）。
    • 示例：若src/ 有main.c 和utils.c，则LIOT_AIROCOV_CUSTOMER_APP_CSRC = src/main.c src/utils.c。

6. 过滤排除文件

  • 作用 ：从源文件列表中移除EXCLUDE_FILES 中指定的文件。
  • 关键点 ：当前EXCLUDE_FILES 为空，所以CFILES =CSRC。

7. 转换 .c 为 .o（中间变量）

  • 作用 ：将源文件列表（*.c）转换为目标文件列表（*.o）。
  • 关键点 ：COBJSTEMP 是临时变量 ，路径仍保留原始目录结构（如src/main.o）。

8. 替换路径为构建目录结构

  • 作用 ：将原始路径替换为构建目录下的相对路径 。
  • 关键点 ：
    • 原始路径：./PLAT/project/stm32f4/arm/apps/customer1/airocov_lierda/src/main.c。
    • 替换后：PLAT/project/stm32f4/arm/apps/customer1/airocov_lierda/src/main.o。
    • 目的 ：避免目标文件路径包含./，确保构建路径一致。
  • 注意 ：此操作可能冗余 （因LIOT_AIROCOV_CUSTOMER_APP_PATH 本身已包含完整路径），但逻辑正确。

9. 生成最终目标文件路径

  • 作用 ：将目标文件添加$(BUILDDIR) 前缀（如build/）。
  • 关键点 ：
    • BUILDDIR 通常为build/ 或build/stm32f4/。
    • 示例：COBJS = build/PLAT/project/stm32f4/arm/apps/customer1/airocov_lierda/src/main.o。

10. 生成预处理文件列表

  • 作用 ：为每个.o 文件生成.pp 预处理文件（用于调试）。
  • 关键点 ：PPFILES 是全局变量，用于后续编译器选项（如-MMD）。

11. 依赖文件包含（条件编译）

  • 作用 ：包含编译生成的依赖文件（.d 和.dd）。
  • 关键点 ：
    • ifneq：仅当目标不是 unilog 时 包含.d 依赖文件（避免日志生成时的干扰）。
    • .d：标准依赖文件（由编译器生成）。
    • .dd：额外依赖文件（可能用于特定工具链）。
  • 注意 ：-include 确保文件不存在时不会报错。

12. 添加 FreeRTOS 头文件路径

  • 作用 ：添加 FreeRTOS 移植层头文件路径。
  • 关键点 ：FreeRTOS 通常需在portable/gcc/ 中定义硬件适配。

13. 将目标文件加入链接列表

  • 作用 ：将应用目标文件加入最终链接的obj-y 列表。
  • 关键点 ：
    • 使用COBJSTEMP（非最终路径 ，即PLAT/project/.../src/main.o）。
    • 潜在问题 ：obj-y 通常要求相对路径 ，但COBJSTEMP 已被替换为相对路径（如PLAT/project/.../src/main.o），符合 Makefile 规范。
    • 正确性 ：此处逻辑正确，因为COBJS 已通过addprefix 生成了完整路径，但obj-y 用的是中间变量COBJSTEMP（其值已替换为相对路径）。

关键逻辑总结

步骤 目的 关键变量
路径定义 构建应用代码根目录 LIOT_AIROCOV_CUSTOMER_APP_PATH
头文件包含 使编译器能找到应用和 BSP 头文件 CFLAGS_INC
源文件收集 获取所有.c 文件（过滤排除文件） LIOT_AIROCOV_CUSTOMER_APP_CFILES
路径转换 生成构建目录下的目标文件路径 LIOT_AIROCOV_CUSTOMER_APP_COBJS
依赖处理 生成编译依赖，支持增量编译 .d/.dd 文件包含
链接列表 将目标文件加入最终可执行文件链接列表 obj-y

潜在问题与建议

  1. 路径冗余 ：
    • 第 8 行的subst 操作可能冗余（因LIOT_AIROCOV_CUSTOMER_APP_PATH 本身是完整路径），可简化为：
    • 但当前逻辑无错误 ，仅稍显冗长。
  2. 递归遍历问题 ：
    • wildcard $(dir)/*.c仅匹配当前目录 ，若源文件在子目录中（如src/utils/utils.c），需额外处理（例如：$(wildcard $(dir)/**.c)，但需 Makefile 4.0+）。

显示内容

如何在设备屏幕上显示内容

以往我们学习单片机的时候，我们会初始化一个和屏幕大小的数组，然后对数组内容进行修改，修改后的数据发送到屏幕上，就可以在屏幕上显示我们设置的数组内容。
而Linux也是通过类似的方式，只不过Linux把显示设备抽象为一个文件，在我们板卡中是/dev/fb0，fb是FrameBuffer的缩写，中文译名为帧缓冲驱动，
Linux抽象出FrameBuffer这个设备来供用户态进程实现直接写屏。 FrameBuffer机制模仿显卡的功能，将显卡硬件结构抽象掉， 可以通过FrameBuffer的读写直接对显存进行操作。 用户可以将FrameBuffer看成是显示内存的一个映像， 将其映射到进程地址空间之后，就可以直接进行读写操作， 而写操作可以立即反应在屏幕上。

如上图所示，屏幕中每个像素的显示颜色由4个byte组成，其实就是ARGB格式

所以，我们对/dev/fb0的数据写入，就是显示数据的写入。所以，我们就可以下发代码实现屏幕的刷新，当然了这些代码不用去背，大致了解原理即可。

ioctl（Input/Output Control）用于对设备进行控制操作，例如配置硬件参数、获取设备信息（如终端、帧缓冲设备 /dev/fb0、串口等）交互。

git 简略使用指南

一、引言

1.1 为什么通过 Git 获取 SDK？

在传统的嵌入式开发中，SDK 常通过网盘或邮件以压缩包（.zip/.7z）形式分发。但在Cat.1 bis开发中，这种方式存在明显短板。通过 Git 接入 SDK，将获得以下核心优势：

  • 实时补丁同步（Real-time Updates）：蜂窝模组 SDK 迭代较快，当有关键 Bug 修复或新功能上线时，无需等待 FAE 手动发送新包，仅需一行命令即可同步远程仓库的最新代码。
  • 透明的版本追溯（Traceability）：每一行代码的变更都有记录（Commit Log）。工程在升级后出现异常，可以通过 Git 的对比功能迅速定位是 SDK 的哪一部分改动影响了逻辑，极大地缩短了排障周期。
  • 极速增量更新（Efficiency）：SDK 源码通常包含大量驱动和协议栈。通过 Git 仅拉取“变化的代码块”，避免了每次重复下载数百兆乃至数 GB 的完整安装包，节省了带宽与存储空间。

1.2 现有 Git 托管平台对比

下表是对目前主流的 Git 托管平台进行了简单横向对比：

平台名称 对比分析
GitHub 资源极丰富，但国内访问受限。
Gitee (码云) 访问速度快，但在处理大型企业级 SDK 仓库的定制化分发上灵活性有限。
GitLab 功能强大但缺乏本土化支持，更新维护成本高。

1.3 Git 客户端安装

● Windows: 推荐安装 Git for Windows。
● Linux/macOS: 使用系统自带包管理器安装（如 sudo apt install git）。

注意：Git安装过程中默认使用Vim打开，对于初学者或非专业开发人员，强烈建议不要选择默认的 Vim。

1. 核心概念 (必读)

在输入命令之前，理解 Git 的“三个区域”至关重要：

  1. 工作区 (Working Directory): 你电脑里能看到的文件夹，你在这里修改文件。
  2. 暂存区 (Staging Area/Index): 一个临时区域，保存了你打算提交的修改（git add 后的状态）。
  3. 版本库 (Repository): 存储所有历史版本的地方（git commit 后的状态）。

基本流程： 修改文件 添加到暂存区 提交到版本库。

建议的最佳实践

  1. 勤提交： 尽量保持原子性提交（一个 Commit 只做一件事），方便回滚。
  2. 写好 Commit Message： 清楚地描述“做了什么”，而不是“更新了代码”。
  3. 不要提交大文件/敏感文件： 使用 .gitignore 文件来忽略不需要版本控制的文件（如密码文件、编译生成的 node_modules 或 dist 目录）。
